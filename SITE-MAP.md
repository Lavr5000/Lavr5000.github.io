# Site Map

Public-safe navigation map for the GitHub Pages site. Links use repository filenames only.

## Client Flows

### Ведомость Order Flow

Files: [vedomost.html](vedomost.html), [vedomost.js](vedomost.js), [vedomost.config.js](vedomost.config.js), [assets/forms2.css](assets/forms2.css)

User-visible flow:

1. The user opens [vedomost.html](vedomost.html).
2. The user chooses a PDF file to process.
3. The user enters an email address for delivery.
4. The user reviews and accepts the required consent checkbox.
5. The user may opt in to additional storage or follow-up if the optional checkbox is shown.
6. The user submits the form.
7. The client calls the public order API.
8. The page shows order progress using user-facing stages such as queued, parsing, and delivered.
9. In free-mode, payment is disabled and the visible path stays focused on file upload, consent, submission, and delivery.
10. If a large file is still processing when the client poll cap is reached, the page shows a calm "processing continues, result will arrive by email" notice (not a "contact manager" error). The scary notice is kept only for an `awaiting_payment` stall. (Shared `assets/order-flow.js`, applies to both ведомость and nakladnaya.)
11. When the order is waiting behind others, the queued view shows how many documents are ahead ("Перед вами в очереди: N …") and an estimated wait time, plus a reminder that the result arrives by email so the tab can be closed. Position and the estimate are shown only while queued; the estimate is hidden when it cannot be computed. (Shared `assets/order-flow.js`.)

Public form fields and ids:

- `email` - email address where the user expects to receive the processing result or status.
- `consent` - required consent checkbox confirming that the user agrees to the linked terms and personal data processing conditions.
- `optin` - optional checkbox for the user-visible extended storage or follow-up option, when enabled by the page.
- `website` - hidden honeypot field intended to remain empty for real users.

Configuration:

- `CONSENT_VERSION` lives in [vedomost.config.js](vedomost.config.js) and identifies the consent text/version submitted with the order. Current value `vedomost-v3-2026-10` (since 2026-10: the text names the cloud recognition service OpenRouter). The `#optin` checkbox stays optional (extended 90-day storage, opt-in). The `vedomost.js` entry script and its internal config import are version-pinned (`?v=vedomost-v3-2026-10`) so the whole client module graph is cache-busted together.
- `PAYMENT_ENABLED` lives in [vedomost.config.js](vedomost.config.js) and controls whether the order UI exposes the paid path or free-mode behavior.

### Rating And Feedback Flow

Files: [rate.html](rate.html), [rate.js](rate.js), [assets/forms2.css](assets/forms2.css), inline rating widget in [vedomost.js](vedomost.js)

User-visible flow:

1. The user opens the feedback UI from [rate.html](rate.html) or from the inline widget shown by the ведомость flow.
2. The user selects the main outcome: "подошла" when the result worked, or "есть замечания" when there were issues.
3. If there are remarks, the user can select one or more visible reasons.
4. The user may add an optional free-text comment.
5. The client posts the feedback to the public rate endpoint.

The rating flow is for product feedback only. It should not expose private processing details to the user.

### Products Catalog

Files: [products.html](products.html), [products.js](products.js), [products.render.js](products.render.js), [scripts/validate_products.mjs](scripts/validate_products.mjs)

The products page is a public append-only catalog. The tiles of the sellable products are static `article.card` markup in [products.html](products.html); [products.js](products.js) is the registry — the single source of truth, validated by `node scripts/validate_products.mjs` with the record count snapshotted in `.github/products-count.txt` — and keeps every product, including the ones that only appear in the «Готовятся» line and never get a card.

A record may carry a `gate`: a snake_case key of a backend switch. Such a record ships `visible: false` and is absent from the static markup; on page load [products.render.js](products.render.js) asks `GET <API_ORIGIN>/api/products/status` (`API_ORIGIN` imported from [vedomost.config.js](vedomost.config.js), the same origin the order forms use; allowed in the page CSP `connect-src`) and adds the card to `#catalog-section .cards` at its `order` position only when the answer for the gate is `"public"`. A network error, a non-200 answer or the 4 s timeout leaves the tile hidden — the static catalog never waits for the request. Currently gated: `pdf_tables` → [pdf-tables.html](pdf-tables.html) (order 70, 499 ₽, `tests/products_tile_check.py`).

New products should be added by appending to the existing registry structure rather than rewriting previous entries, so old public links and catalog behavior stay stable.

### Printed M-15 Delivery Notes Flow

Files: [nakladnaya.html](nakladnaya.html), [nakladnaya.js](nakladnaya.js), [assets/order-flow.js](assets/order-flow.js)

User-visible flow:

1. The user opens [nakladnaya.html](nakladnaya.html).
2. The user uploads one PDF scan of printed M-15 delivery notes.
3. The user enters an email address and accepts the required product-scoped OCR consent (`m15-v1`).
4. The client creates an order for product `nakladnaya-m15`, uploads the PDF, shows payment when required, polls status, and shows delivered/error states.
5. The backend returns the Excel result by email after OCR processing.

Public form fields and ids:

- `file` - one PDF scan of printed M-15 delivery notes.
- `email` - email address where the result is delivered.
- `consent` - required OCR consent checkbox for external OpenRouter processing.
- `website` - hidden honeypot field intended to remain empty for real users.

### PDF Tables Flow («Таблицы из PDF», gated)

Files: [pdf-tables.html](pdf-tables.html), [pdf-tables.js](pdf-tables.js), [pdf-tables.config.js](pdf-tables.config.js), [tests/pdf_tables_check.py](tests/pdf_tables_check.py)

User-visible flow (consent → order → upload → pre-check → pay 499 → status):

1. The user opens [pdf-tables.html](pdf-tables.html) — from the catalog tile, itself hidden until the backend switch `pdf_tables` answers `public` (see Products Catalog above).
2. The user accepts the required consent (`pdf-tables-v1-2026-10`: sheets go to cloud recognition via OpenRouter only to build the result, only tables that passed the automatic check are delivered, full refund when none passed), enters an email and uploads one PDF (up to 25 sheets, vector tables or a text layer — not a scan).
3. The client creates the order; the server pre-checks the file BEFORE any payment — a file that fails the pre-check never gets a payment link.
4. Pre-check passed → the «Оплатить 499 ₽» button opens the bank page; on return the page resumes by the order token saved in sessionStorage.
5. Status ladder: проверка → оплата → извлечение → готово; the Excel with the verified tables and the note on what was not delivered and why arrives by email. Zero verified tables, a technical failure or a missed deadline refunds the payment automatically.

## Machine-Readable Endpoints

### IDmaster NTD channel (`idm/`)

Files: [idm/version.json](idm/version.json), `idm/ntd-snapshot.<sha256>.json`, [idm/last-check.json](idm/last-check.json), [scripts/ntd/](scripts/ntd/), [.github/workflows/idm-ntd-publish.yml](.github/workflows/idm-ntd-publish.yml)

Not a page: three static JSON files read by the desktop IDmaster workbook when its user presses «Обновить нормативы». No human visitor is expected here and nothing links to it.

- `idm/version.json` — the distribution manifest: workbook `version`, the URL of the current NTD snapshot and its sha256. Name is stable.
- `idm/ntd-snapshot.<sha256>.json` — a snapshot of the Rosstandart SP registry (all statuses). The file name carries the sha256 of its own content, so a client holding an older manifest keeps resolving the snapshot that manifest promises, and a mid-publication download can never mismatch.
- `idm/last-check.json` — the run-unique `check_id`, timestamp and counters of the last channel check; it is how the workflow proves the deploy actually reached the live site, and it keeps the weekly schedule from being auto-disabled for inactivity.

`.github/workflows/idm-ntd-publish.yml` rebuilds and republishes weekly. It writes only `idm/`, dispatches the existing Pages deploy explicitly (a `GITHUB_TOKEN` commit does not trigger it by push), and fails the run if the change is not observable on `ai-vibes.ru`. Pull requests touching `scripts/ntd/**` run the same collector in a read-only dry mode.

### Search and AI crawler files

Files: [robots.txt](robots.txt), [sitemap.xml](sitemap.xml), [llms.txt](llms.txt), the JSON-LD block of [index.html](index.html) and [services/index.html](services/index.html), [scripts/build_seo_files.py](scripts/build_seo_files.py), [tests/seo_files_check.py](tests/seo_files_check.py), [.github/workflows/seo-files.yml](.github/workflows/seo-files.yml)

Since 2026-10-03 the site tells search engines and AI assistants what it is. All five outputs are **generated** from the pages themselves — never edited by hand.

- `robots.txt` — one group for every crawler: `/docs/`, `/idm/` and `/scripts/` are closed, everything else is open (AI crawlers included), plus the `Sitemap:` line.
- `sitemap.xml` — the list of public pages. A page gets in when it carries a self-referencing `<link rel="canonical">` on `https://ai-vibes.ru/…` and no `noindex`; pages without a canonical (search-engine verification files, `apartment-auditor/privacy-policy.html`) drop out by themselves. No `lastmod`, so the file changes only when a page appears or disappears.
- `llms.txt` — a plain-text summary in the llmstxt.org format: the site name and description, the services with their prices (read off the `a[data-pay]` and `a[data-request]` links of `/services/` and `/products.html`; records of [services.js](services.js) marked `archived: true` are skipped), the contacts of the `#contact` block, and every sitemap page with its title and meta description.
- JSON-LD — one `<script type="application/ld+json">` before `</head>` between the markers `<!-- seo:jsonld:begin (scripts/build_seo_files.py) -->` and `<!-- seo:jsonld:end -->`: `WebSite`, `Organization` and `Person` on the main page; `Organization`, `Person` and one `Service` with its `Offer` per tariff `a[data-pay]` on `/services/` (price from `data-price-label`, url `/services/#service-5` and `/services/#vip`). A rerun replaces the block; the line endings of the file are kept. `build_seo_files.py` and `build_chrome.py` own different regions of the pages, so they give the same result in any order.
- **New page or changed price:** run `python scripts/build_seo_files.py --write` and commit the result (`--check` verifies, no flag is a dry run; last line `SEO_FILES status=ok pages=N files=`). If that is forgotten, `seo-files.yml` does it: on a push to `master` that touches a page it regenerates, runs the test, commits as `seo-files-bot` when something changed and dispatches the Pages deploy.
- **After pushing pages the `seo-files.yml` bot may add its own commit to `master` — run `git fetch` and rebase before the next push.**
- `python tests/seo_files_check.py [--root DIR]` is the offline gate: the generator's `--check`, the sitemap against the canonical rule in both directions (`/spasibo/` is `noindex` and stays out), `robots.txt` read by RFC 9309 for six crawlers, every price and phrase of `llms.txt` found word for word in the pages, no archived service, Hermes or `#pokaz` in the generated files, exactly one parsable JSON-LD block per page with one `Service` per tariff `a[data-pay]`, and a scratch-copy run proving that the two generators leave the tree unchanged in the orders seo→chrome→seo and chrome→seo→chrome. It carries six negative probes.

### Services Page

Files: [services/index.html](services/index.html), [services.js](services.js), [services.config.js](services.config.js), [scripts/validate_services.mjs](scripts/validate_services.mjs), [assets/pay.js](assets/pay.js)

- Two tariffs, «Старт» (7 500 ₽) and VIP (45 000 ₽), plus monthly support (5 000 ₽) and the two document services of [products.html](products.html). The full tariff cards live on this page only; the main page repeats the two tariffs with the same registry ids, so a wording or price change is made in the registry and in both cards.
- [services.js](services.js) is the append-only registry: an immutable kebab-case `id` per service plus the one `title` used on the site, in the offer terms, in the payment link and on the receipt, `pricingModel` (`fixed` | `from`), `priceLabel.ru` (the exact rendered string) and `unit`. A record with `archived: true` (the three old setup services) is kept only so its id stays valid: it is not shown on the site, not written to the SEO files and has no buttons.
- **Whitespace canon for prices:** every price string uses U+0020 only, никаких NBSP и `&nbsp;` — otherwise the byte-for-byte comparison between registry, button and card is meaningless. The validator rejects a string that merely *renders* the same.
- `node scripts/validate_services.mjs` gates three halves: the registry schema (unique ids, non-empty fields, name length within the 64-character receipt cap, `priceLabel` agreeing with `price` and `pricingModel`, `archived` only as `true`); every button of [index.html](index.html), [services/index.html](services/index.html) and [products.html](products.html) — `a[data-pay]` and `a[data-request]` — resolving to a known non-archived id whose `title` equals `data-order` and `priceLabel` equals `data-price-label` byte for byte (a pay link also needs `data-amount` = price×100 and a non-empty `href`); and the visible price of the card carrying the button (`.tariff-price` in `article[data-tariff]`, `.card-price` in `article.card`) equal to the same label.
- **Tariff buttons and payment.** A pay button is a plain link (`href="/#contact"`, it works without scripts): `<a data-pay data-service-id data-order data-price-label data-amount>`. [services.config.js](services.config.js) defines `window.AI_PAY` with the switch `enabled`. While `enabled` is `false` (the default) the button reads «Заказать за …» and opens the request dialog `dialog#order-dialog` with three channels: MAX first, then Telegram, then a prefilled mailto; nothing is charged and no API call is made. When `enabled` is `true` the button opens the payment dialog `dialog#pay-dialog` (e-mail for the receipt, contact, consent) and sends the order to the order API; the customer is redirected to an allow-listed bank host and comes back to `/spasibo/`. The payment window and its fields carry Metrika's `ym-hide-content` / `ym-disable-keys` classes.
